# AP-00: spike x402 Stellar

Fecha: 25 de septiembre de 2026. Rama: `feat/agentic-payments`. Estado: **parcial**. Ningún pago fue ejecutado por este spike.

## Evidencia reproducible

Los paquetes `@x402/core`, `@x402/express`, `@x402/stellar` y `@x402/fetch` se fijaron en `2.27.0` en `apps/api`. Su licencia declarada en npm es Apache-2.0; `@x402/stellar` declara Node `>=22`. PaperPay debe mantener esa versión mínima si adopta esta combinación.

La prueba `apps/api/test/agentic/x402-spike.test.ts` monta el middleware oficial con un facilitador falso que anuncia `exact` en `stellar:testnet`. Comprueba que la respuesta HTTP 402 contiene `PAYMENT-REQUIRED`, que no filtra el texto protegido y que `x402HTTPClient` decodifica el reto con `x402Version: 2`, `amount: "5000000"` y la tesorería esperada. Ejecutar con `pnpm --filter @paperpay/api test`.

El comando `pnpm --filter @paperpay/api test:agentic-capability` consulta exclusivamente `/supported` con `HTTPFacilitatorClient` y falla si no encuentra `exact`/`stellar:testnet`. El 25 de septiembre, `https://www.x402.org/facilitator` anunció ese par con `areFeesSponsored: true`. La respuesta de capacidades es un dato actual del proveedor, no una garantía permanente.

`https://channels.openzeppelin.com/x402/testnet/supported` respondió 401 sin credencial. Para consultarlo desde el probe, usar `X402_FACILITATOR_URL` y `X402_FACILITATOR_API_KEY` en el entorno del proceso. La documentación de OpenZeppelin indica `Authorization: Bearer <key>` para `/supported`, `/verify` y `/settle`; el probe solo consulta `/supported`.

El SDK ofrece hooks `onBeforeVerify`, `onAfterVerify`, `onBeforeSettle`, `onAfterSettle` y `onSettleFailure`. El cliente HTTP declara que un timeout de `/settle` deja un resultado indeterminado: la transferencia podría haberse completado. Los hooks ofrecen puntos para registrar el intento; por sí solos no crean un recibo durable ni una consulta de estado del proveedor.

## Pendiente para cerrar AP-00

- Comprar un recurso de prueba con `@x402/fetch` y una wallet Testnet dedicada que tenga USDC, sin emplear las cuentas privadas existentes del proyecto.
- Capturar el reto, el payload firmado y la respuesta de pago en fixtures sanitizados; guardar hash, ledger y versión exacta de paquetes.
- Repetir con un cliente ajeno al cliente PaperPay y comprobar la misma ruta.
- Inducir pérdida de respuesta después del envío y demostrar un método de conciliación inequívoco. No asumir que el hash de la transacción es conocido antes de que el facilitador responda.
- Probar `/supported` del facilitador autenticado seleccionado y los límites de payload, fees, timeout y secuencias.
- Confirmar que el middleware permite registrar la asignación de una autorización a un artículo antes de llamar a `/settle`, incluso cuando el handler o la base de datos falla.

Hasta cerrar estas pruebas, no se habilitará `/api/v2` para cobrar. El test usa un facilitador falso y solo verifica formato y descubrimiento; no verifica liquidación, entrega ni recuperación.
